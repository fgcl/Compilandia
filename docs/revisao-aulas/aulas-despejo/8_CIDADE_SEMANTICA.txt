################ ASSUNTO ATTRIBUTES_TYPES: Atributos e verificação de tipos  prereqs=[CFG_DERIVATION]
FICHA: Uma SDD pendura atributos nos símbolos da gramática: sintetizados sobem dos filhos, herdados descem do pai/irmãos; a verificação de tipos é uma SDD que calcula tipos e insere coerções.
  gancho: S↑ H↓: Sintetizado Sobe, Herdado desce. S-atribuída = Só Sintetizado; L-atribuída = herda da Left.
  termos: [sintetizado, herdado, s-atribuída, l-atribuída, coerção, tipo]
  erros comuns: [Chamar de herdado um atributo calculado a partir dos filhos, Achar que L-atribuída permite depender de irmãos à direita, Esquecer que toda S-atribuída também é L-atribuída, Tratar int + float como erro em vez de coerção para float, Confundir erro de tipo (compilação) com divisão por zero (execução)]
  FLASH: Atributo sintetizado depende de... -> Atributos dos filhos (e do próprio nó)
  FLASH: Atributo herdado depende de... -> Atributos do pai e dos irmãos
  FLASH: O que é SDD S-atribuída? -> Só tem atributos sintetizados
  FLASH: O que é SDD L-atribuída? -> Herdados dependem só do pai e de irmãos à esquerda
  FLASH: Ordem de avaliação de uma S-atribuída? -> Pós-ordem (de baixo para cima)
  FLASH: Tipo de int + float? -> float, com inttofloat no int
  FLASH: Tipo de a < b? -> bool
  FLASH: Em int a, b, c, o tipo chega às variáveis como... -> Atributo herdado
  FLASH: $$ = $1 + $3 no Bison é que tipo de atributo? -> Sintetizado

=== AULA DE LEITURA [STORY] Notas que sobem, sobrenomes que descem
[NARRADOR] Cidade Semântica. A árvore sintática já está pronta... mas ela ainda não sabe o que significa.
[BYTE] Como assim? A árvore de 'a + x * 2' tá certinha!
[PROF] Ela está certa na FORMA. Agora precisamos pendurar informação em cada nó: tipo, valor, código... Esses penduricalhos são os **atributos**.
TEXTO: Pense na sua média do semestre: a nota final é calculada a partir das notas das provas, que vêm dos exercícios. A informação **sobe**. Isso é um atributo **sintetizado**.
TEXTO: Agora pense no sobrenome: você o recebe dos pais e repassa aos irmãos mais novos. A informação **desce** (ou vem do lado). Isso é um atributo **herdado**.
PASSOS O mapa da analogia:
    1. Nota final calculada das parciais → **sintetizado** (do filho para o pai)
    2. Sobrenome vindo dos pais → **herdado** (do pai ou irmão para o filho)
    3. Regulamento de como calcular a média → **regra semântica** (E.tipo = ...)
    4. Gramática + atributos + regras → **definição dirigida pela sintaxe (SDD)**
TEXTO: O fiscal da balança da feira é o **verificador de tipos**: não deixa somar banana com bool. Mas int com float pode, é só converter o int, como trocar reais por dólares antes de somar. Isso é **coerção**.
PREVEJA: a é int e x é float. Qual o tipo de a + x * 2?
    (     ) int
    (certa) float, com coerção de int para float
    (     ) erro de tipo
    EXPLICACAO: x * 2 é float (2 é convertido). a + float também vira float: o compilador converte a com inttofloat.
WIDGET ATTR_TREE gramatica= entrada=a + x * 2 legenda=Os tipos sobem das folhas até a raiz: int + float → float.
REVELAR: Em 'int a, b, c;', o tipo int é sintetizado ou herdado para cada variável?
    RESPOSTA: Herdado: ele desce do nó do tipo para a lista de nomes, como um sobrenome passado aos irmãos.
DESTAQUE NO_DUMB_QUESTIONS: 'Atributo é só uma variável no nó?' Basicamente, sim! O que importa é DE ONDE vem o valor dela: dos filhos (sintetizado) ou do pai/irmãos (herdado).

=== AULA DE LEITURA [SOCRATIC] De onde vem a informação de cada nó?
[PROF] Pergunta-guia de hoje: para calcular este atributo, eu preciso olhar PARA BAIXO ou PARA CIMA?
REVELAR: O valor de E em E → E1 + T depende de quê?
    RESPOSTA: De E1.val e T.val: dos filhos. É sintetizado.
REVELAR: Se TODOS os atributos são sintetizados, em que ordem dá para avaliar?
    RESPOSTA: Pós-ordem (de baixo para cima). Uma SDD assim é **S-atribuída** e combina perfeitamente com um analisador LR: avalia na hora da redução.
REVELAR: E em D → T L, com 'int a, b, c', como cada id descobre seu tipo?
    RESPOSTA: Pelo atributo herdado L.in = T.tipo, que desce pela lista. O id está abaixo e à direita de quem sabe o tipo.
[BYTE] Então herdado pode vir de qualquer lugar?
REVELAR: Se um atributo herdado pudesse depender de um irmão à DIREITA, um analisador que lê da esquerda para a direita conseguiria calcular na hora?
    RESPOSTA: Não: o irmão da direita ainda não foi analisado. Daí a restrição L-atribuída.
PREVEJA: Numa SDD **L-atribuída**, o atributo herdado de Xi em A → X1 X2 ... Xn pode depender de...
    (     ) Qualquer atributo de qualquer filho
    (certa) Atributos herdados de A e atributos de X1 ... Xi-1 (irmãos à esquerda)
    (     ) Apenas atributos sintetizados de A
    EXPLICACAO: L de Left: só o pai (herdados dele) e os irmãos à esquerda. Assim uma passada em profundidade, da esquerda para a direita, resolve tudo, perfeito para descida recursiva.
REVELAR: Toda SDD S-atribuída é L-atribuída?
    RESPOSTA: Sim! Ela não tem herdados, então a restrição é satisfeita trivialmente.
REVELAR: Por que o verificador de tipos precisa da tabela de símbolos?
    RESPOSTA: Porque nas folhas só há nomes. O tipo de 'a' foi decidido lá na declaração; a tabela é a memória que liga uso e declaração.
WIDGET ATTR_TREE gramatica= entrada=a + b * c legenda=Pós-ordem em ação: b * c primeiro, depois a soma.
DESTAQUE BRAIN_POWER: Se o grafo de dependências entre atributos tiver um ciclo, não existe ordem de avaliação. S-atribuída e L-atribuída são duas classes que garantem: sem ciclos.

=== AULA DE LEITURA [FORMAL] SDD, atributos e sistema de tipos
TEXTO: **Definição dirigida pela sintaxe (SDD):** gramática livre de contexto + atributos associados aos símbolos + regras semânticas associadas às produções.
PASSOS Tipos de atributo (para um não-terminal A num nó N):
    1. **Sintetizado:** definido por regra da produção em que A é a CABEÇA, usando atributos dos filhos de N e do próprio N
    2. **Herdado:** definido por regra da produção em que A está no CORPO (no pai de N), usando atributos do pai, dos irmãos e do próprio N
    3. Terminais só têm atributos sintetizados, fornecidos pelo léxico (ex.: num.lexval)
PASSOS Classes de SDD:
    1. **S-atribuída:** só atributos sintetizados → avaliação em pós-ordem; implementável durante a análise LR
    2. **L-atribuída:** em A → X1...Xn, cada herdado de Xi depende só de herdados de A e de atributos de X1...Xi-1 (e de Xi, sem ciclo) → uma passada em profundidade, esquerda para direita
    3. **Esquema de tradução (SDT):** gramática com fragmentos de programa {ações} embutidos no corpo; em SDD S-atribuída, as ações vão no fim (SDT pós-fixo)
CODIGO (SDD L-atribuída clássica: declarações (in é herdado)):
    D → T L ;        L.in = T.tipo
    T → int          T.tipo = int
    T → float        T.tipo = float
    L → L1 , id      L1.in = L.in ;  addType(id.entrada, L.in)
    L → id           addType(id.entrada, L.in)
CODIGO (Verificação de tipos com coerção (alargamento)):
    E → E1 op E2   (op aritmético):
      se E1.tipo = bool ou E2.tipo = bool: erro de tipo
      E.tipo := max(E1.tipo, E2.tipo)      // int < float
      E.addr1 := widen(E1.addr, E1.tipo, E.tipo)   // insere inttofloat se preciso
      E.addr2 := widen(E2.addr, E2.tipo, E.tipo)
    E → E1 relop E2:  numéricos → E.tipo := bool
    E → E1 && E2:     ambos bool → E.tipo := bool
PREVEJA: Uma coerção int → float inserida pelo compilador é chamada de...
    (     ) Conversão explícita (cast)
    (certa) Coerção implícita (alargamento)
    (     ) Estreitamento
    EXPLICACAO: Coerção = conversão implícita feita pelo compilador. int → float é alargamento (não perde a ordem de grandeza). float → int seria estreitamento e costuma exigir cast explícito.
WIDGET ATTR_TREE gramatica= entrada=a + x * 2 legenda=Instância da regra acima: max(int, float) = float, com widen em a.
DESTAQUE EXAM_TIP: Ao classificar uma SDD, verifique CADA regra que define um herdado: ela usa algum irmão à direita? Se sim, não é L-atribuída. Sem herdados → S-atribuída (e também L).
DESTAQUE WATCH_OUT: Verificação de tipos é estática (em tempo de compilação). Divisão por zero com valores de variáveis só aparece em tempo de execução, não é erro de tipo.

=== AULA DE LEITURA [SOCRATIC] Uma tabela só não bastaria?

[NARRADOR] Véspera de prova de Literatura. Byte tem duas opções: reler o livro inteiro, com prefácio, índice e notas de rodapé, ou ler o resumo de duas páginas da colega.

PASSOS Livro × resumo → árvore de derivação × AST:

    3. Numeração e índice → **parênteses e pontuação**: só serviam para o parser saber a ordem. A forma da AST já guarda essa ordem.
    4. Páginas em branco → produções **ε**: somem.
    5. Personagens e ações → **operadores e operandos**: viram nós `BinOp`, `Var`, `Num`.

=== AULA DE LEITURA [WORKED] Construindo a AST na descida recursiva
[PROF] Lembra do parser descendente recursivo, com um método por não-terminal? A mudança é pequena: em vez de void, cada método **devolve uma Expr**.
CODIGO (As classes da AST (Java, como no trabalho prático)):
    abstract class Expr { }
    class Num extends Expr { int valor;  Num(int v) { valor = v; } }
    class Var extends Expr { String nome; Var(String n) { nome = n; } }
    class BinOp extends Expr {
        char op; Expr esq, dir;
        BinOp(char op, Expr esq, Expr dir) { this.op = op; this.esq = esq; this.dir = dir; }
    }
CODIGO (O parser que CONSTRÓI a AST. O while em expr() e termo() garante associatividade à esquerda.):
    Expr expr() {                 // E → T (('+'|'-') T)*
        Expr e = termo();
        while (tok.equals("+") || tok.equals("-")) {
            char op = tok.charAt(0); casaToken(tok);
            e = new BinOp(op, e, termo());   // associa à esquerda
        }
        return e;
    }
    Expr termo() {                // T → F (('*'|'/') F)*
        Expr e = fator();
        while (tok.equals("*") || tok.equals("/")) {
            char op = tok.charAt(0); casaToken(tok);
            e = new BinOp(op, e, fator());
        }
        return e;
    }
    Expr fator() {                // F → ( E ) | id | num
        if (tok.equals("(")) { casaToken("("); Expr e = expr(); casaToken(")"); return e; }
        if (ehNumero(tok)) { int v = Integer.parseInt(tok); casaToken(tok); return new Num(v); }
        String nome = tok; casaToken(tok); return new Var(nome);
    }
PASSOS Rastreando '2 * x + y':
    1. expr() chama termo(); termo() chama fator().
    2. fator() vê '2' (número) → devolve **new Num(2)**. Em termo(), e = Num(2).
    3. termo() vê '*': casa, chama fator(), que devolve **Var(x)**. e = **new BinOp('*', Num(2), Var(x))**.
    4. termo() vê '+', que não é * nem /: sai do while e devolve o BinOp('*').
    5. De volta em expr(): e = BinOp('*'). Vê '+': casa, chama termo(), que devolve **Var(y)**.
    6. e = **new BinOp('+', BinOp('*', Num(2), Var(x)), Var(y))**. Fim da entrada: devolve e.
WIDGET AST gramatica= entrada=2 * x + y legenda=Confira: 13 nós na derivação, 5 na AST, e o código Java gerado.
DESTAQUE WATCH_OUT: A linha mais importante é `e = new BinOp(op, e, termo());`: o resultado ANTERIOR vira o filho ESQUERDO do novo nó. É assim que 'a - b - c' vira (a - b) - c. Se você escrever recursão (`e = new BinOp(op, e, expr())`), a árvore fica pendurada para a direita e a subtração dá errado.

=== AULA DE LEITURA [FORMAL] AST: definição de prova
TEXTO: **Árvore de derivação (concreta)**: raiz = símbolo inicial; cada nó interno é um não-terminal A cujos filhos são o lado direito de uma produção A → α usada; folhas, lidas da esquerda para a direita, formam a sentença.
TEXTO: **Árvore sintática abstrata (AST)**: cada nó interno é um **operador ou construção** da linguagem e seus filhos são os **operandos/componentes** com significado. Omite não-terminais de cadeia (A → B), parênteses, pontuação e ε. A AST não é única da gramática: é uma escolha de projeto do compilador.
CODIGO (Comandos como classes (junto com Expr, Num, Var, BinOp)):
    abstract class Cmd { }
    
    class Atrib extends Cmd {          // x = expr;
        String var; Expr valor;
    }
    class Se extends Cmd {             // if (cond) entao else senao
        Expr cond; Cmd entao, senao;   // senao == null quando não há else
    }
    class Enquanto extends Cmd {       // while (cond) corpo
        Expr cond; Cmd corpo;
    }
    class Bloco extends Cmd {          // { c1 c2 ... }
        List<Cmd> cmds = new ArrayList<>();
    }
TEXTO: **Construção dirigida pela sintaxe**: cada produção recebe uma regra semântica que sintetiza o atributo `nodo` (a AST do lado esquerdo) a partir dos `nodo` dos filhos. É uma definição **S-atribuída**: os atributos sobem da folha para a raiz.
CODIGO (No Bison (ascendente): $$ é o valor do lado esquerdo; $1, $2, $3 os dos símbolos do lado direito):
    exp   : exp '+' termo     { $$ = new BinOp('+', $1, $3); }
          | exp '-' termo     { $$ = new BinOp('-', $1, $3); }
          | termo             { $$ = $1; }          /* corrente: só repassa */
          ;
    termo : termo '*' fator   { $$ = new BinOp('*', $1, $3); }
          | fator             { $$ = $1; }
          ;
    fator : '(' exp ')'       { $$ = $2; }          /* o parêntese SOME aqui */
          | ID                { $$ = new Var($1); }
          | NUM               { $$ = new Num($1); }
          ;
PREVEJA: Na regra `fator : '(' exp ')' { $$ = $2; }`, por que $2?
    (     ) Porque o parêntese é o 2º símbolo
    (certa) Porque exp é o 2º símbolo do lado direito, e a AST do fator é simplesmente a AST de exp
    (     ) Para criar um nó de parênteses
    EXPLICACAO: '(' é $1, exp é $2, ')' é $3. Repassar $2 é exatamente 'jogar fora o parêntese'.
TEXTO: **Descendente recursivo**: cada método de não-terminal devolve a AST do que reconheceu. Para A → A op B (recursiva à esquerda, eliminada como A → B (op B)*), use um **laço** que acumula: `e = new BinOp(op, e, B())`, preservando a associatividade à esquerda.
CODIGO (Percorrendo a AST: cada fase é um método (ou um Visitor). Repare na pós-ordem: filhos antes do pai.):
    abstract class Expr {
        abstract int avaliar(Map<String, Integer> mem);
        abstract String gerar(Gerador g);          // devolve onde ficou o valor
    }
    class Num extends Expr {
        int valor;
        int avaliar(Map<String, Integer> mem) { return valor; }
        String gerar(Gerador g) { return String.valueOf(valor); }
    }
    class Var extends Expr {
        String nome;
        int avaliar(Map<String, Integer> mem) { return mem.get(nome); }
        String gerar(Gerador g) { return nome; }
    }
    class BinOp extends Expr {
        char op; Expr esq, dir;
        int avaliar(Map<String, Integer> mem) {
            int x = esq.avaliar(mem), y = dir.avaliar(mem);   // filhos primeiro (pós-ordem)
            switch (op) { case '+': return x + y; case '-': return x - y;
                          case '*': return x * y; default:  return x / y; }
        }
        String gerar(Gerador g) {
            String x = esq.gerar(g), y = dir.gerar(g);
            String t = g.novoTemp();
            g.emite(t + " = " + x + " " + op + " " + y);       // TAC!
            return t;
        }
    }
DESTAQUE REAL_WORLD: Com muitas fases, em vez de pôr avaliar/gerar/verificarTipo em cada classe, usa-se o padrão **Visitor**: uma classe por fase (VerificadorDeTipos, GeradorMips) com um método visitar por tipo de nó. javac, Roslyn (C#) e o Clang são organizados em torno da AST assim.
DESTAQUE EXAM_TIP: Três perguntas que caem: (1) desenhar a AST de uma expressão (lembre: sem parênteses, associativa à esquerda); (2) escrever as ações $$ = new ... de uma gramática Bison; (3) 'diferencie árvore de derivação de AST', responda com a definição + um exemplo com contagem de nós.
REVELAR: Defina AST e cite três coisas que ela descarta em relação à árvore de derivação.
    RESPOSTA: Árvore em que nós internos são operadores/construções e filhos são operandos com significado. Descarta: não-terminais de cadeia (E → T → F), parênteses/pontuação e produções ε (e, com elas, as palavras-chave que só marcavam a construção).

=== AULA DE LEITURA [MNEMONIC] A árvore de dieta
DESTAQUE MNEMONIC: **AST = Árvore Sem Tralha.** Tira três tralhas: **C**orrentes (E → T → F), **P**arênteses (e pontuação) e **E**psilons. 'Corta o CPE.'
TEXTO: **Palácio da memória**: na Cidade Semântica, ao lado do cartório da tabela de símbolos, fica a **Fábrica de AST** , uma marcenaria. Chega um tronco enorme (a árvore de derivação); o marceneiro serra os galhos que só passam adiante, joga a serragem dos parênteses fora e entrega uma mesa de 5 peças, pronta para uso.
DESTAQUE MNEMONIC: **Parênteses são andaimes**: indispensáveis enquanto o prédio está sendo construído (parsing), retirados quando ele fica pronto. A forma do prédio (a árvore) já guarda o que eles seguravam.
DESTAQUE MNEMONIC: **Corrente de WhatsApp**: E → T → F → a é como mensagem encaminhada cinco vezes. O conteúdo é o 'a'; os encaminhamentos não acrescentam nada. Na AST: Var(a), e só.
DESTAQUE MNEMONIC: **Quem está mais fundo trabalha primeiro.** Na AST de a + b * c, o * está no porão: é feito antes. Profundidade = precedência.
PREVEJA: Qual linha de código é o 'segredo' da associatividade à esquerda no parser descendente?
    (     ) return new BinOp(op, termo(), expr());
    (certa) e = new BinOp(op, e, termo()); dentro de um while
    (     ) if (tok.equals("(")) return expr();
    EXPLICACAO: 'O velho vai para a esquerda': o resultado acumulado vira filho esquerdo do novo nó, a cada volta do laço.
DESTAQUE MNEMONIC: **Bison em três palavras: 'filho vira pai'.** $$ = new BinOp('+', $1, $3), os filhos $1 e $3 se tornam filhos do nó novo $$. Corrente? $$ = $1. Parêntese? $$ = $2.
DESTAQUE WATCH_OUT: Contrastes que confundem: **árvore de derivação** tem não-terminais e todos os tokens; a **AST** tem só operadores e operandos. **AST** é estrutura; **TAC** é uma lista de instruções gerada a partir dela. **Parse tree** = árvore de derivação = árvore sintática concreta (três nomes, uma coisa).
WIDGET AST gramatica= entrada=( a + b ) * c legenda=Corta o CPE: conte as correntes, os parênteses e veja 18 virar 5.
REVELAR: Sem olhar: o que é jogado fora, o que fica e onde mora a precedência?
    RESPOSTA: Fora: correntes, parênteses/pontuação, ε. Fica: operadores (BinOp) e operandos (Var, Num), e construções (Atrib, Se, Enquanto, Bloco). Precedência e associatividade moram na FORMA da árvore.
REVELAR: Por que vale a pena montar a AST no TP em vez de gerar código direto no parser?
    RESPOSTA: Porque aí o compilador pode percorrer o programa várias vezes (tipos, depois código), com cada fase separada e testável, e otimizar mexendo na árvore. Tradução direta é uma passada só, sem volta.
