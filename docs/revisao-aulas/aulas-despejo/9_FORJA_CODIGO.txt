################ ASSUNTO TAC: Código de três endereços  prereqs=[ATTRIBUTES_TYPES]
FICHA: Código de três endereços é uma linguagem intermediária com no máximo um operador por instrução (x = y op z), gerada em pós-ordem com temporários, e representada como quádruplas ou triplas.
  gancho: Dois entram, um sai. QUAdrupla = QUAtro campos; a TRIpla mora no endereço (posição).
  termos: [temporário, três endereços, quádrupla, tripla, pós-ordem, rótulo]
  erros comuns: [Colocar dois operadores numa instrução (t = a + b * c), Gerar o pai antes dos filhos (a ordem é pós-ordem), Em triplas, dar nome ao resultado em vez de usar a posição, Esquecer o goto para pular o else num if-else]
  FLASH: Forma geral da instrução? -> x = y op z
  FLASH: Quantos operadores por instrução? -> No máximo um
  FLASH: TAC de a + b * c? -> t1 = b * c; t2 = a + t1
  FLASH: Campos da quádrupla? -> op, arg1, arg2, resultado
  FLASH: Campos da tripla? -> op, arg1, arg2 (resultado = posição)
  FLASH: Por que triplas indiretas? -> Para reordenar sem quebrar referências
  FLASH: Ordem de geração numa expressão? -> Pós-ordem da árvore
  FLASH: Como vira um if em TAC? -> Desvios condicionais, goto e rótulos

=== AULA ANIMADA [BASICO] Uma conta por linha  (id=TAC, ~146s, 21 passos, exemplo começa no passo 3)
1. [BYTE] O processador faz uma conta por vez, sempre com dois valores.
     palco: TAC | a + b * c | processador | uma conta por vez
2. [BYTE] Quantas contas há nessa linha? Toque no número.
     palco: TAC | *a + b * c | processador | uma conta por vez | 1 | 2 | 3
     PERGUNTA(toque): certas=[2] erradas=[1, 3]
       dica: Conte os operadores. Cada um é uma conta.
       acerto: Isso. Duas contas, então duas linhas.
3. [BYTE] O código de três endereços é um código intermediário: cada linha faz uma conta só, com no máximo três nomes.
     palco: TAC
4. [BYTE] Primeiro a árvore sintática. Ela já diz qual conta vem antes.
     palco: a + b * c | + | a | * | b | c
5. [BYTE] Qual conta tem que sair primeiro? Toque no operador.
     palco: a + b * c | + | a | * | b | c
     PERGUNTA(toque): certas=[*] erradas=[+]
       dica: A árvore manda: quem está mais fundo vem antes.
       acerto: Isso. O vezes está mais fundo.
6. [BYTE] O resultado do vezes não tem nome no programa. O compilador cria um temporário para ele, o t1.
     palco: a + b * c | + | a | ** | b | c | *t1 = b * c
7. [BYTE] Na linha seguinte, a árvore já pode usar o t1 no lugar do vezes.
     palco: a + b * c | *+ | a | * | b | c | t1 = b * c | *t2 = a + t1
8. [PROF] Cada linha tem no máximo três endereços: dois operandos e um resultado. É daí que vem o nome.
     palco: a + b * c | + | a | * | b | c | t1 = b * c | t2 = a + t1
9. [BYTE] A ordem das linhas saiu da árvore. E esse código ainda não depende de nenhum processador.
     palco: a + b * c | + | a | * | b | c | t1 = b * c | t2 = a + t1
10. [BYTE] Para gerar as linhas, ande pela árvore de baixo para cima.
     palco: Receita | 1. Gere os filhos antes do pai. | 2. Cada operador ganha um temporário novo. | 3. O pai usa o temporário do filho. | 4. Atribuição: copie o último temporário.
11. [BYTE] Por que o vezes saiu antes do mais? Toque na regra.
     palco: Receita | 1. Gere os filhos antes do pai. | 2. Cada operador ganha um temporário novo. | 3. O pai usa o temporário do filho. | 4. Atribuição: copie o último temporário.
     PERGUNTA(toque): certas=[1. Gere os filhos antes do pai.] erradas=[2. Cada operador ganha um temporário novo., 3. O pai usa o temporário do filho., 4. Atribuição: copie o último temporário.]
       dica: Na árvore, o vezes é filho do mais.
       acerto: Isso. Filho antes do pai.
12. [BYTE] Regra três: na segunda linha, o t1 ocupa o lugar do vezes.
     palco: Receita | 1. Gere os filhos antes do pai. | 2. Cada operador ganha um temporário novo. | *3. O pai usa o temporário do filho. | 4. Atribuição: copie o último temporário.
13. [BYTE] Agora quem gera é você. No fim, o resultado vai para o x.
     palco: x = ( a + b ) * ( c - d ) | * | + | a | b | - | c | d
14. [BYTE] Qual operador vira o t1? Toque nele.
     palco: x = ( a + b ) * ( c - d ) | * | + | a | b | - | c | d
     PERGUNTA(toque): certas=[+] erradas=[-, *]
       dica: O vezes espera os dois filhos. Comece pelo filho da esquerda.
       acerto: Isso. A soma vira o t1.
15. [BYTE] A soma virou t1. Qual operador vira o t2? Toque.
     palco: x = ( a + b ) * ( c - d ) | * | t1 | - | c | d | t1 = a + b
     PERGUNTA(toque): certas=[-] erradas=[*]
       dica: O vezes ainda espera o filho da direita.
       acerto: Isso. A subtração vira o t2.
16. [BYTE] Agora a raiz. Toque na linha que o vezes gera.
     palco: x = ( a + b ) * ( c - d ) | ** | t1 | t2 | t1 = a + b | t2 = c - d | t3 = a * d | t3 = t1 * t2 | t3 = t1 * c - d
     PERGUNTA(toque): certas=[t3 = t1 * t2] erradas=[t3 = a * d, t3 = t1 * c - d]
       dica: Regra três: use os temporários dos filhos.
       acerto: Isso. Três endereços: t3, t1 e t2.
17. [BYTE] Falta guardar no x. Qual temporário vai para ele? Toque.
     palco: x = ( a + b ) * ( c - d ) | t3 | t1 = a + b | t2 = c - d | t3 = t1 * t2 | t3 | t2 | t1
     PERGUNTA(toque): certas=[t3] erradas=[t2, t1]
       dica: Regra quatro: o último temporário, o da raiz.
       acerto: Isso. A última linha só copia o valor.
18. [BYTE] Quatro linhas, e nenhuma faz mais de uma conta. Na etapa de prática, o if e o while também viram linhas, com rótulos e desvios.
     palco: x = ( a + b ) * ( c - d ) | t3 | *t1 = a + b | *t2 = c - d | *t3 = t1 * t2 | *x = t3
19. [BYTE] Esta atribuição cabe numa linha de três endereços? Um colega disse que sim. Certo ou errado?
     palco: Erros comuns | x = a + b * c cabe numa linha só de três endereços. | certo | errado
     PERGUNTA(toque): certas=[errado] erradas=[certo]
       dica: Conte os nomes: x, a, b e c. Quantos cabem numa linha?
       acerto: Isso. São duas contas e quatro nomes. Cada linha leva um operador e no máximo três endereços.
20. [BYTE] Outro erro: reaproveitar o t1 na segunda conta. Se o valor antigo ainda for usado, ele se perde. Cada resultado ganha um temporário novo.
     palco: Erros comuns | Certo: São duas linhas: t1 = b * c, depois x = a + t1. | *Errado: Reusar o mesmo temporário para duas contas diferentes. | *Certo: Cada operador ganha um temporário novo: t1, t2, t3...
21. [BYTE] Resumindo: o código de três endereços quebra a expressão em contas simples. A árvore dá a ordem, e cada resultado parcial ganha um temporário.
     palco: Resumo | Três endereços: resultado = operando operador operando. | Gere os filhos antes do pai; cada conta guarda num temporário novo. | É código intermediário: não depende do processador.

=== AULA ANIMADA [PRATICA] if e while viram desvios  (id=TAC/ifewhileviramdesvios, ~74s, 9 passos, exemplo começa no passo null)
1. [BYTE] Até aqui, o código de três endereços só fez contas. Mas programa tem if e while, e a máquina não tem nenhum dos dois.
     palco: if / while | if (a < b) x = 1; | else x = 2;
2. [BYTE] A máquina só sabe seguir para a próxima linha ou desviar para uma linha marcada com um rótulo.
     palco: if / while | if (a < b) x = 1; | else x = 2; | rótulo:  L1: | desvio:  goto L1
3. [BYTE] Primeiro a condição vira uma conta, guardada em t1. Depois vem o desvio condicional: se t1 for falso, pule para L1.
     palco: if / while | if (a < b) x = 1; | else x = 2; | *    t1 = a < b | *    ifFalse t1 goto L1
4. [BYTE] Se a condição é verdadeira, a execução segue para a próxima linha. Que comando vem ali? Toque.
     palco: if / while | if (a < b) x = 1; | else x = 2; |     t1 = a < b | *    ifFalse t1 goto L1 | x = 1 | x = 2
     PERGUNTA(toque): certas=[x = 1] erradas=[x = 2]
       dica: É o comando que roda quando a é menor que b.
       acerto: Isso. O bloco do if vem logo depois do desvio condicional.
5. [BYTE] Depois de x igual a um, o que impede a execução de cair no else? Toque.
     palco: if / while | if (a < b) x = 1; | else x = 2; |     t1 = a < b |     ifFalse t1 goto L1 | *    x = 1 | goto L2 | L1: | nada
     PERGUNTA(toque): certas=[goto L2] erradas=[L1:, nada]
       dica: Sem nada ali, a próxima linha é a do else.
       acerto: Isso. Um desvio incondicional pula o else e vai para o fim, no rótulo L2.
6. [BYTE] O rótulo L1 marca o começo do else. O L2 marca o fim do if inteiro.
     palco: if / while | if (a < b) x = 1; | else x = 2; |     t1 = a < b |     ifFalse t1 goto L1 |     x = 1 |     goto L2 | *L1: x = 2 | *L2:
7. [BYTE] O while usa as mesmas peças. O rótulo fica antes da condição, e no fim do corpo um goto volta para ele.
     palco: while | while (i < n) i = i + 1; | *L1: t1 = i < n |     ifFalse t1 goto L2 |     i = i + 1 |     goto L1 | L2:
8. [BYTE] No while, para onde vai o goto do fim do corpo? Toque na linha.
     palco: while | while (i < n) i = i + 1; | L1: t1 = i < n |     ifFalse t1 goto L2 |     i = i + 1 | *    goto L1 | L2:
     PERGUNTA(toque): certas=[L1: t1 = i < n] erradas=[    ifFalse t1 goto L2, L2:]
       dica: O laço precisa testar a condição de novo.
       acerto: Isso. Ele volta para a condição, que é testada a cada volta.
9. [BYTE] O if e o while viram três peças: rótulo, desvio condicional e desvio incondicional. É assim que o seu laço chega ao MIPS.
     palco: while | while (i < n) i = i + 1; | L1: t1 = i < n |     ifFalse t1 goto L2 |     i = i + 1 |     goto L1 | L2:

=== AULA DE LEITURA [STORY] A receita para o ajudante que só faz uma coisa por vez
[NARRADOR] Forja do Código. A árvore anotada chega numa esteira; do outro lado, sai uma lista de instruções.
[BYTE] Por que não transformar a árvore direto em Assembly?
[PROF] Porque existem dezenas de processadores. É mais esperto traduzir para uma linguagem intermediária simples, e só no fim para cada máquina.
TEXTO: Imagine uma receita para um ajudante de cozinha que só sabe fazer **uma operação por vez**, com **no máximo dois ingredientes**, e sempre coloca o resultado **numa tigela com etiqueta**.
CODIGO ('Junte b com c (multiplicando) na tigela t1; depois junte a com t1 na tigela t2.' — a + b * c):
    t1 = b * c
    t2 = a + t1
PASSOS O mapa da analogia:
    1. Uma operação por vez, dois ingredientes → **instrução de três endereços**: x = y op z
    2. Tigelas com etiqueta t1, t2... → **temporários** gerados pelo compilador
    3. Ordem da receita → **pós-ordem** da árvore: filhos antes do pai
    4. Ficha com 4 campos (operação, ingr. 1, ingr. 2, tigela) → **quádrupla**
    5. Ficha sem tigela: 'use o resultado do passo 0' → **tripla**
PREVEJA: Quantas instruções (sem contar a atribuição final) para a + b * c - a?
    (     ) 2
    (certa) 3
    (     ) 4
    EXPLICACAO: Três operadores → três instruções: t1 = b * c; t2 = a + t1; t3 = t2 - a.
WIDGET TAC gramatica= entrada=a + b * c legenda=A máquina de receitas: a multiplicação vem primeiro porque está mais embaixo na árvore.
[PILHA] Tigelas... são como eu. Guardam... resultados no meio do caminho.
REVELAR: Por que 'três endereços'?
    RESPOSTA: Porque cada instrução menciona no máximo três nomes: dois operandos e um destino (x = y op z).
DESTAQUE REAL_WORLD: O LLVM IR é uma linguagem intermediária no espírito do TAC (em forma SSA): Clang, Rust e Swift geram LLVM IR, e o LLVM o traduz para x86, ARM, RISC-V...

=== AULA DE LEITURA [VISUAL] Da árvore à lista, em pós-ordem
[PROF] Vamos ver a árvore e o código lado a lado.
WIDGET ATTR_TREE gramatica= entrada=a + b * c legenda=A árvore: '*' está embaixo, '+' na raiz.
WIDGET TAC gramatica= entrada=a + b * c legenda=Pós-ordem: b * c gera t1; depois a + t1 gera t2.

    (     ) t1 = x * 2; t2 = a + t1
    (certa) t1 = x * 2; t2 = inttofloat(a); t3 = t2 + t1

=== AULA DE LEITURA [WORKED] Expressões, quádruplas, triplas e um if
[PROF] Exercício 1: gere TAC para x = (a + b) * (a - c).
PASSOS Pós-ordem, com calma:
    1. Subárvore esquerda a + b → t1 = a + b
    2. Subárvore direita a - c → t2 = a - c
    3. Raiz * → t3 = t1 * t2
    4. Atribuição → x = t3
CODIGO (Duas representações das mesmas instruções):
    quádruplas                      triplas
         op  arg1  arg2  res             op  arg1  arg2
    (0)  +   a     b     t1        (0)   +   a     b
    (1)  -   a     c     t2        (1)   -   a     c
    (2)  *   t1    t2    t3        (2)   *   (0)   (1)
    (3)  =   t3          x         (3)   =   x     (2)
[PROF] Exercício 2: comandos com desvio. if (a < b) x = 1; else x = 2;
CODIGO (Rótulos e desvios: o if vira 'pule se for falso'):
        ifFalse a < b goto L1
        x = 1
        goto L2
    L1: x = 2
    L2: ...
[BYTE] Agora eu faço!
REVELAR: TAC de y = a * b + a * b.
    RESPOSTA: t1 = a * b; t2 = a * b; t3 = t1 + t2; y = t3. (Sim, a * b duas vezes, o gerador ingênuo não otimiza.)
REVELAR: As triplas de y = a * b + a * b.
    RESPOSTA: (0) * a b; (1) * a b; (2) + (0) (1); (3) = y (2).
REVELAR: TAC de while (a < b) a = a + 1;
    RESPOSTA: L1: ifFalse a < b goto L2;  t1 = a + 1;  a = t1;  goto L1;  L2: ...
WIDGET TAC gramatica= entrada=a * b + a * b legenda=Confira a primeira resposta.
DESTAQUE EXAM_TIP: Em triplas, o resultado é referenciado pela POSIÇÃO: (2) * (0) (1). Na prova, numere as linhas desde o começo, senão as referências viram bagunça.

=== AULA DE LEITURA [SOCRATIC] Por que uma linguagem no meio do caminho?
[PROF] Pergunta 1: se eu tenho 5 linguagens-fonte e 4 processadores, quantos compiladores completos eu escrevo sem código intermediário?
REVELAR: E com uma representação intermediária comum?
    RESPOSTA: Sem: 5 × 4 = 20 compiladores. Com: 5 front-ends + 4 back-ends = 9 peças. A IR é o 'adaptador universal'.
REVELAR: Por que limitar a no máximo um operador por instrução?
    RESPOSTA: Porque se parece com instruções de máquina (um op por vez), torna a ordem de avaliação explícita e facilita otimizar e alocar registradores.
REVELAR: Em que ordem as instruções de uma expressão aparecem?
    RESPOSTA: Na pós-ordem da árvore: cada operador só pode ser calculado depois dos seus operandos.
[BYTE] E de onde saem os nomes t1, t2...?
REVELAR: Quem cria os temporários?
    RESPOSTA: O próprio compilador (new Temp()), um por nó operador. Eles não existem no programa-fonte.
PREVEJA: Por que quádruplas são mais fáceis de reordenar do que triplas?
    (     ) Porque ocupam menos memória
    (certa) Porque nas triplas os resultados são referenciados pela posição; mover uma instrução quebra as referências
    (     ) Porque triplas não aceitam desvios
    EXPLICACAO: Na quádrupla o resultado tem nome (t1); na tripla ele é '(0)'. Mudou a posição, mudou o nome. Por isso existem as triplas INDIRETAS (uma lista de ponteiros que se reordena).
REVELAR: Como representar um if em TAC, se não há chaves nem blocos?
    RESPOSTA: Com rótulos e desvios: ifFalse cond goto L1, goto L2, L1: ... A estrutura vira um grafo de saltos.
WIDGET TAC gramatica= entrada=(a + b) * c legenda=Teste: preveja as instruções antes de olhar.
DESTAQUE BRAIN_POWER: O TAC é baixo nível o bastante para ficar perto da máquina e alto o bastante para não depender dela. Esse equilíbrio é o que torna a otimização portátil.

=== AULA DE LEITURA [FORMAL] Instruções de três endereços e representações
TEXTO: **Código de três endereços:** sequência de instruções com, no máximo, um operador no lado direito. Um 'endereço' pode ser um nome do programa, uma constante ou um temporário gerado pelo compilador.
CODIGO (Formas de instrução (Livro do Dragão, seção 6.2)):
    x = y op z          atribuição binária
    x = op y            atribuição unária (menos, not, conversão)
    x = y               cópia
    goto L              desvio incondicional
    if x goto L         desvio condicional
    ifFalse x goto L
    if x relop y goto L
    param x;  call p, n;  y = call p, n;  return y
    x = y[i];  x[i] = y         acesso indexado
    x = &y;  x = *y;  *x = y    endereços e ponteiros
CODIGO (SDD de tradução de expressões para TAC (|| = concatenação)):
    S → id = E ;   S.code := E.code || gen(top.get(id.lexeme) '=' E.addr)
    E → E1 + E2    E.addr := new Temp()
                   E.code := E1.code || E2.code || gen(E.addr '=' E1.addr '+' E2.addr)
    E → - E1       E.addr := new Temp()
                   E.code := E1.code || gen(E.addr '=' 'minus' E1.addr)
    E → ( E1 )     E.addr := E1.addr;  E.code := E1.code
    E → id         E.addr := top.get(id.lexeme);  E.code := ''
PASSOS Representações:
    1. **Quádruplas:** (op, arg1, arg2, resultado), resultado nomeado; fácil de reordenar
    2. **Triplas:** (op, arg1, arg2), o resultado é a posição da instrução; economiza espaço
    3. **Triplas indiretas:** lista de ponteiros para triplas; reordena-se a lista
    4. **SSA:** cada variável é atribuída uma única vez (x1, x2...), com funções φ nas junções
PREVEJA: Qual NÃO é uma instrução de três endereços válida?
    (     ) t1 = a + b
    (certa) t2 = a + b * c
    (     ) if t1 goto L3
    EXPLICACAO: t2 = a + b * c tem dois operadores. Precisa virar t1 = b * c; t2 = a + t1.
WIDGET TAC gramatica= entrada=a + b - c legenda=Associatividade à esquerda: (a + b) primeiro, depois - c.
DESTAQUE EXAM_TIP: Questão comum: 'traduza para quádruplas E triplas'. Faça primeiro o TAC em texto, numere as linhas, e só então preencha as duas tabelas.

=== AULA DE LEITURA [STORY] A lista de compras inteligente
[NARRADOR] Forja do Código, sala de polimento. O TAC chega meio bruto; aqui ele sai brilhando.
[BYTE] Otimizar é deixar o código ÓTIMO?
[PROF] O nome engana: é **melhorar**, sem mudar o resultado do programa. 'Ótimo' de verdade é impossível de garantir. Vamos pensar numa lista de compras.
TEXTO: Sua lista diz: 'comprar 2 × 6 ovos'. Você faz a conta **em casa**, não no caixa: 12 ovos. Isso é **dobra de constantes**: calcular em tempo de compilação.
TEXTO: A lista diz 'comprar leite' duas vezes, e nada mudou entre uma e outra. Você compra uma vez só e usa as duas. Isso é eliminar **subexpressão comum**.
TEXTO: A lista tem 'comprar fermento', mas nenhuma receita usa. Corta! Isso é eliminar **código morto**.
PASSOS O mapa da analogia:
    1. Fazer a conta em casa → **dobra de constantes** (2 * 6 vira 12)
    2. Anotar 'ovos = 12' e usar 12 dali em diante → **propagação de constantes**
    3. Comprar leite uma vez só → **eliminação de subexpressões comuns**
    4. Riscar o fermento que ninguém usa → **eliminação de código morto**
    5. Trecho do mercado sem desvios, entra e sai por um lugar só → **bloco básico**
PREVEJA: Qual linha pode ser calculada inteiramente pelo compilador?
    (     ) t1 = a * 2
    (certa) t1 = 2 * 3
    (     ) t1 = x * y
    EXPLICACAO: Só 2 * 3 depende apenas de constantes. Vira t1 = 6 antes do programa rodar.
WIDGET TAC gramatica= entrada=2 * 3 + a legenda=O gerador produz t1 = 2 * 3; com dobra de constantes, sobra só uma instrução: 6 + a.
DESTAQUE WATCH_OUT: Regra de ouro: otimização NUNCA pode mudar o que o programa faz. Na dúvida (efeitos colaterais, divisão por zero...), o compilador não otimiza.
REVELAR: Na analogia, por que 'comprar leite' duas vezes só pode virar uma se 'nada mudou entre uma e outra'?
    RESPOSTA: Se alguém tivesse bebido o leite no meio (uma variável redefinida), a segunda compra seria necessária. Subexpressão comum só vale sem redefinição dos operandos.

=== AULA DE LEITURA [SOCRATIC] Quando é seguro otimizar?
[PROF] A otimização tem um juramento: não mudar o comportamento. Vamos testar esse juramento com perguntas.
REVELAR: x = 10 / 0 pode ser 'dobrado' pelo compilador?
    RESPOSTA: Não como valor: a divisão por zero precisa acontecer (ou ser reportada). O dobrador do jogo, inclusive, se recusa a dobrar isso.
REVELAR: E t = 0.1 + 0.2 com float?
    RESPOSTA: Pode, desde que o compilador use exatamente a mesma aritmética da máquina-alvo. Senão o resultado mudaria.
REVELAR: Quando duas ocorrências de a + b são a 'mesma' subexpressão?
    RESPOSTA: Quando nem a nem b foram redefinidos entre elas (e não há efeito colateral, como chamada de função que altera a ou b).
[BYTE] E código morto: como o compilador sabe que ninguém usa?
REVELAR: O que significa uma variável estar 'viva' num ponto?
    RESPOSTA: Que o valor dela pode ser usado depois, num caminho de execução, antes de ser redefinido. Atribuição a variável não viva é código morto.
PREVEJA: if (false) { print(1); }, o que a otimização pode fazer?
    (     ) Nada
    (certa) Remover o bloco inteiro: é código inalcançável
    (     ) Trocar por print(0)
    EXPLICACAO: Com a condição constante, o desvio sempre pula o bloco. Inalcançável = pode sair.
REVELAR: Por que dividir o código em blocos básicos antes de otimizar?
    RESPOSTA: Dentro de um bloco não há desvios para dentro nem para fora no meio: as instruções executam todas, em ordem. Fica fácil raciocinar sobre valores.
REVELAR: x * 2 → x + x ou x << 1: que otimização é essa?
    RESPOSTA: Redução de força: trocar uma operação cara por uma equivalente mais barata.
WIDGET TAC gramatica= entrada=2 * 3 + a legenda=Preveja o código depois da dobra antes de olhar.
DESTAQUE BRAIN_POWER: Pense numa expressão com chamada de função: f() + f(). É subexpressão comum? Só se f não tiver efeitos colaterais, e o compilador quase nunca consegue provar isso sozinho.

=== AULA DE LEITURA [FORMAL] Blocos básicos e transformações que preservam a semântica
TEXTO: **Bloco básico:** sequência maximal de instruções consecutivas em que o fluxo só entra pela primeira e só sai pela última, sem desvios no meio. **Grafo de fluxo:** blocos como nós; arestas para os sucessores possíveis.
CODIGO (Particionamento em blocos básicos (Livro do Dragão, Alg. 8.5)):
    LÍDERES:
      1. a primeira instrução do código é líder
      2. toda instrução que é ALVO de um desvio (condicional ou não) é líder
      3. toda instrução que vem IMEDIATAMENTE APÓS um desvio é líder
    BLOCOS:
      cada líder inicia um bloco, que vai até a instrução
      anterior ao próximo líder (ou até o fim)
PASSOS Transformações clássicas:
    1. **Dobra de constantes:** avaliar em compilação operações com operandos constantes (2 * 3 → 6)
    2. **Propagação de constantes:** após x = 6, substituir usos de x por 6 enquanto x não for redefinido
    3. **Subexpressões comuns:** E já calculada e operandos não redefinidos desde então → reutilizar o valor
    4. **Propagação de cópias:** após x = y, usar y no lugar de x
    5. **Código morto:** remover instruções cujo resultado não está vivo (nunca usado depois)
    6. **Redução de força / movimentação de código invariante de laço:** trocar ops caras; tirar do laço o que não muda nele
TEXTO: **Local** = dentro de um bloco básico (ex.: via DAG do bloco). **Global** = sobre o grafo de fluxo, com análise de fluxo de dados (variáveis vivas, definições que alcançam, expressões disponíveis).
PREVEJA: Qual transformação exige saber quais variáveis estão VIVAS?
    (     ) Dobra de constantes
    (certa) Eliminação de código morto
    (     ) Redução de força
    EXPLICACAO: Só é seguro apagar x = ... se o valor de x não for usado depois. 'Vivo' é exatamente isso.
WIDGET TAC gramatica= entrada=x * 2 + 3 * 4 legenda=Dobra de constantes local: 3 * 4 → 12.
DESTAQUE EXAM_TIP: Questão clássica: 'identifique os líderes e os blocos básicos'. Marque líderes com as 3 regras, numerando as instruções; depois desenhe o grafo de fluxo com as arestas de desvio E de queda (fall-through).
DESTAQUE WATCH_OUT: A instrução APÓS um desvio é líder, e não a do desvio. O goto/if fecha o bloco; ele é a ÚLTIMA instrução do bloco.

=== AULA DE LEITURA [MNEMONIC] DOPA SUMO e o PAD dos blocos

=== AULA DE LEITURA [STORY] A pilha de pratos da cozinha
[NARRADOR] Forja do Código, fim de expediente. O código já foi gerado... mas, quando ele RODA, onde moram as variáveis de cada função?
[BYTE] Na memória, ué. Cada variável tem o seu lugarzinho fixo, não tem?
[PROF] Quase! Pense na cozinha de um restaurante em dia de movimento. Cada pedido que começa vira um prato na pilha da bancada, com um bilhete grudado.
TEXTO: O bilhete diz: **quais ingredientes** vieram no pedido, **para qual mesa** devolver o prato pronto e tem um espaço para os **rascunhos** do cozinheiro. E ele só mexe no prato do **topo**.
TEXTO: Se, no meio de um prato, ele precisa de um molho que é outra receita, põe um **prato novo em cima**, faz o molho, tira esse prato e volta para o de baixo exatamente de onde parou.
PASSOS O mapa da analogia:
    1. Cada pedido em preparo → uma **ativação** (uma chamada de função em andamento)
    2. Prato com bilhete → **registro de ativação** (ou **quadro**, *frame*)
    3. Ingredientes do pedido → **parâmetros**
    4. Para qual mesa devolver → **endereço de retorno** (no MIPS, o registrador `$ra`)
    5. Rascunhos do cozinheiro → **variáveis locais** e **temporários**
    6. Pilha de pratos na bancada → **pilha de execução**: só o topo trabalha
    7. Molho que precisa de outro molho da MESMA receita → **recursão**: vários pratos iguais empilhados
[PILHA] Prato novo... vai em cima. Prato pronto... sai de cima. Eu nunca... tiro do meio.
CODIGO (O fatorial recursivo: uma receita que pede a si mesma):
    1 int fat(int n) {
    2   if (n <= 1) return 1;
    3   return n * fat(n - 1);
    4 }
    5 int main() {
    6   return fat(3);
    7 }
PREVEJA: Rodando fat(3), quantos pratos (registros de ativação) ficam empilhados no momento MAIS alto, contando o de main?
    (     ) 2
    (     ) 3
    (certa) 4
    (     ) 6
    EXPLICACAO: main → fat(3) → fat(2) → fat(1): quatro quadros ao mesmo tempo. Só quando fat(1) devolve 1 a pilha começa a baixar. Se você chutou 3, esqueceu do prato do main, erro supercomum!
WIDGET CALL_STACK gramatica= entrada=fat3 legenda=Empilhe e desempilhe: cada fat(n) tem o SEU próprio n no bilhete.
DESTAQUE NO_DUMB_QUESTIONS: 'Se todos os quadros são da mesma função fat, por que o n não se mistura?' Porque cada chamada ganha um prato NOVO, com o seu próprio n. O n=3 fica guardadinho embaixo enquanto o n=1 trabalha no topo.
TEXTO: E o resto da cozinha? O **cardápio** pregado na parede é o **código**; as **placas fixas** (nome da casa, horário) são a **área estática** (variáveis globais); o **depósito**, de onde se pega e devolve caixa a qualquer hora, é o **heap** (`new`, `malloc`).
REVELAR: Por que o depósito (heap) existe, se a pilha já funciona tão bem?
    RESPOSTA: Porque o prato da pilha é jogado fora quando a função termina. Se você precisa de algo que viva DEPOIS do retorno, um objeto criado com `new`, uma lista que cresce, ele vai para o heap.
DESTAQUE REAL_WORLD: Recursão sem caso base = pratos empilhados até o teto. Em Java isso é o famoso `StackOverflowError`; em C, geralmente um *segmentation fault*. É o prato batendo no lustre.

=== AULA DE LEITURA [VISUAL] A pilha de chamadas, quadro a quadro
[PROF] Hoje a gente assiste à memória durante a execução. Primeiro, um programa sem recursão: main chama f, que chama g, que chama h.
CODIGO (f chama g, g chama h... e f ainda chama h de novo):
    1 int h(int a) {
    2   return a + 1;
    3 }
    4 int g(int b) {
    5   return h(b * 2);
    6 }
    7 int f(int c) {
    8   return g(c) + h(c);
    9 }

    11  return f(1);
    12 }
WIDGET CALL_STACK gramatica= entrada=chain1 legenda=Avance passo a passo: cada chamada EMPILHA um quadro; cada return DESEMPILHA.
PASSOS O que você acabou de ver:
    1. main chama f(1): pilha [main, f]
    2. f chama g(1): [main, f, g]
    3. g chama h(2): [main, f, g, h], o ponto mais alto, 4 quadros
    4. h devolve 3 e sai; g devolve 3 e sai: [main, f]
    5. f chama h(1) DE NOVO: [main, f, h], o mesmo h, um quadro novinho
    6. h devolve 2; f devolve 3 + 2 = 5; main devolve 5
[BYTE] O h apareceu duas vezes, em alturas diferentes da pilha!
[PROF] Exato. O quadro depende de QUEM chamou e QUANDO, não só do nome da função. Por isso cada quadro guarda o seu próprio endereço de retorno.
PREVEJA: Agora fat(4). Qual a altura máxima da pilha, contando main?
    (     ) 4
    (certa) 5
    (     ) 8
    EXPLICACAO: main + fat(4) + fat(3) + fat(2) + fat(1) = 5. Regra prática: profundidade da recursão + 1 (o main).
WIDGET CALL_STACK gramatica= entrada=fat4 legenda=Confira: a pilha sobe até fat(1) e depois desce devolvendo 1, 2, 6, 24.
TEXTO: Agora uma recursão que **ramifica**: fib(3) chama fib(2) e fib(1). O desenho de TODAS as chamadas forma a **árvore de ativação**.
CODIGO (Árvore de ativação de fib(3): 6 ativações no total (com main)):
              main
               |
             fib(3)
            /      \
        fib(2)    fib(1)
        /    \
    fib(1)  fib(0)
WIDGET CALL_STACK gramatica= entrada=fib3 legenda=Repare: em cada instante, a pilha é o CAMINHO da raiz até o nó que está executando.
PREVEJA: Em fib(3), no instante em que fib(0) executa, quem está na pilha?
    (     ) main, fib(3), fib(2), fib(1), fib(0)
    (certa) main, fib(3), fib(2), fib(0)
    (     ) Só fib(0)
    EXPLICACAO: O fib(1) da esquerda já terminou e saiu. A pilha guarda só os ancestrais vivos: main → fib(3) → fib(2) → fib(0). Altura máxima de fib3: 4.
DESTAQUE BRAIN_POWER: A árvore de ativação conta a história inteira; a pilha mostra só o 'agora'. Percorrer a árvore em profundidade (desce = chama, sobe = retorna) é exatamente o que a pilha faz.

=== AULA DE LEITURA [WORKED] fat(3) na mão: e em MIPS
[PROF] Exercício clássico: rode fat(3) à mão, mostrando a pilha de registros de ativação e os valores devolvidos.
CODIGO (O programa):
    1 int fat(int n) {
    2   if (n <= 1) return 1;
    3   return n * fat(n - 1);
    4 }
    5 int main() {
    6   return fat(3);
    7 }
PASSOS Resolvido, chamada por chamada:
    1. 1. main chama fat(3): quadro {n=3, volta para: main, linha 6}
    2. 2. 3 > 1, então fat(3) precisa de fat(2): quadro {n=2, volta para: fat, linha 3}
    3. 3. fat(2) chama fat(1): quadro {n=1, volta para: fat, linha 3}. Pilha: main, fat(3), fat(2), fat(1) — 4 quadros
    4. 4. fat(1) cai no caso base, devolve 1 e o seu quadro é desempilhado
    5. 5. fat(2) retoma na linha 3: 2 * 1 = 2; devolve 2 e sai
    6. 6. fat(3) retoma: 3 * 2 = 6; devolve 6 e sai
    7. 7. main recebe 6
TEXTO: Agora o mesmo fatorial em MIPS, do jeito que o MARS roda. O quadro de cada chamada tem 2 palavras (8 bytes): o `$ra` e o `n`.
CODIGO (fat.asm: prólogo abre o quadro, epílogo fecha):
            .text
    main:   li   $a0, 3            # argumento: n = 3
            jal  fat               # chama fat; $ra = endereço da linha de baixo
            move $a0, $v0          # o resultado chega em $v0
            li   $v0, 1            # syscall 1: imprimir inteiro
            syscall                # imprime 6
            li   $v0, 10           # syscall 10: encerrar
            syscall
    
    fat:    addi $sp, $sp, -8      # PRÓLOGO: abre o quadro (2 palavras)
            sw   $ra, 4($sp)       # guarda o endereço de retorno
            sw   $a0, 0($sp)       # guarda n
            slti $t0, $a0, 2       # $t0 = (n < 2)
            beq  $t0, $zero, REC   # n >= 2? vai para a recursão
            li   $v0, 1            # caso base: devolve 1
            addi $sp, $sp, 8       # fecha o quadro
            jr   $ra
    REC:    addi $a0, $a0, -1      # argumento n - 1
            jal  fat               # $v0 = fat(n - 1)

            lw   $ra, 4($sp)       # recupera o SEU endereço de retorno
            addi $sp, $sp, 8       # EPÍLOGO: fecha o quadro

            jr   $ra               # volta para quem chamou
PASSOS Quem faz o quê na chamada:
    1. **Chamador:** põe o argumento em `$a0` e executa `jal fat` (que guarda o endereço de volta em `$ra`)
    2. **Chamado, na entrada (prólogo):** `addi $sp, $sp, -8` abre o quadro; salva `$ra` e `$a0` nele
    3. **Chamado, na saída (epílogo):** põe o resultado em `$v0`, restaura `$ra`, `addi $sp, $sp, 8` fecha o quadro e `jr $ra` volta
    4. **Chamador, depois:** usa o valor que chegou em `$v0`

=== AULA DE LEITURA [SOCRATIC] Por que uma PILHA?
[PROF] Vamos reinventar o ambiente de execução só com perguntas. Responda de cabeça antes de tocar, errar aqui é parte do método.
REVELAR: Ideia mais simples: cada variável de cada função ganha um endereço fixo (alocação estática). O que dá errado com fat(3)?
    RESPOSTA: Só existe UM n para a função fat. Quando fat(2) escreve n=2, destrói o n=3 que fat(3) ainda vai usar na volta. Alocação estática não suporta recursão (o FORTRAN antigo nem permitia recursão por isso).
REVELAR: Então cada CHAMADA precisa da sua própria cópia de n. Em que ordem essas cópias nascem e morrem?
    RESPOSTA: A última chamada a começar é a primeira a terminar (LIFO): fat(1) nasce por último e morre primeiro. Esse é exatamente o comportamento de uma pilha.
[BYTE] Tá, mas além do n, o que mais o quadro precisa guardar?
REVELAR: Quando fat(1) termina, como a máquina sabe para onde voltar?
    RESPOSTA: Ela guardou o **endereço de retorno** na hora da chamada. No MIPS, `jal` coloca esse endereço em `$ra`; como a próxima chamada sobrescreveria `$ra`, ele é salvo no quadro.
REVELAR: E como devolver o resultado e voltar a usar o quadro de quem chamou?
    RESPOSTA: O resultado vai num lugar combinado (no MIPS, `$v0`). Para reencontrar o quadro anterior, guarda-se o **vínculo de controle** (link dinâmico), um ponteiro para o quadro do chamador — ou, no MIPS simples, basta desfazer o `$sp`.
PREVEJA: Quem deve ABRIR o espaço das variáveis LOCAIS de uma função?
    (     ) O chamador, porque ele sabe quantos parâmetros passa
    (certa) O chamado, porque só ele sabe quantas locais e temporários tem
    (     ) O sistema operacional
    EXPLICACAO: O tamanho das locais é 'segredo' do chamado (o chamador pode até ter sido compilado antes). Regra geral: o chamador cuida do que conhece (parâmetros, endereço de retorno); o chamado cuida do resto.
REVELAR: Uma função cria uma lista e a devolve para quem chamou. A lista pode morar no quadro dela?
    RESPOSTA: Não! O quadro é desempilhado no retorno, e quem chamou ficaria com um ponteiro para lixo (ponteiro pendente). Coisas que precisam sobreviver à chamada vão para o **heap**.
REVELAR: Recursão infinita: o que acontece com a pilha?
    RESPOSTA: Cada chamada empilha um quadro e nenhuma sai. A pilha cresce até invadir uma área proibida: **estouro de pilha** (stack overflow).
[BYTE] E passar parâmetro por referência? Muda alguma coisa no quadro?
REVELAR: Em swap(x, y) por VALOR, o que vai para o quadro? E por REFERÊNCIA?
    RESPOSTA: Por valor: CÓPIAS de x e y, trocar as cópias não muda nada lá fora. Por referência: os ENDEREÇOS de x e y, o chamado escreve direto nas variáveis do chamador, e a troca acontece de verdade.
WIDGET CALL_STACK gramatica= entrada=fib3 legenda=Teste: antes de cada passo, preveja se a pilha sobe ou desce.
DESTAQUE BRAIN_POWER: Repare no que você acabou de deduzir: pilha (por causa do LIFO), endereço de retorno, vínculo de controle, heap e passagem de parâmetros. É isso que o capítulo 7 do Livro do Dragão formaliza. Você não é 'burro': você acabou de reinventar um ambiente de execução.

=== AULA DE LEITURA [FORMAL] Organização da memória e registros de ativação
TEXTO: **Ambiente de execução** (*run-time environment*): o conjunto de estruturas que o código gerado usa para rodar, organização da memória, registros de ativação, sequências de chamada e passagem de parâmetros.
CODIGO (Subdivisão típica da memória em tempo de execução (Livro do Dragão, seção 7.1)):
    endereços altos
    +----------------------+
    |        PILHA         |  topo em $sp; cresce para BAIXO
    |          v           |
    |                      |
    |          ^           |
    |         HEAP         |  cresce para CIMA (new, malloc)
    +----------------------+
    |  ESTÁTICO  (.data)   |  globais e constantes; tamanho fixo
    +----------------------+
    |  CÓDIGO    (.text)   |  as instruções do programa
    +----------------------+
    endereços baixos
CODIGO (Registro de ativação (quadro): campos típicos (seção 7.2.2)):
    +--------------------------------+
    | parâmetros reais               |  preenchidos pelo CHAMADOR
    | valor de retorno               |
    | vínculo de controle (dinâmico) |  -> quadro do chamador
    | vínculo de acesso (estático)   |  -> quadro do escopo envolvente
    | estado salvo da máquina        |  endereço de retorno, registradores
    | dados locais                   |  preenchidos pelo CHAMADO
    | temporários                    |
    +--------------------------------+
PASSOS Sequência de chamada e de retorno:
    1. **Chamador:** avalia os parâmetros reais e os coloca onde o chamado espera (no quadro, ou em `$a0`–`$a3`)
    2. **Chamador:** registra o endereço de retorno e o vínculo de controle; desvia para o chamado (`jal`)
    3. **Chamado (prólogo):** aloca o quadro (`$sp` -= tamanho), salva registradores (incluindo `$ra`) e inicializa as locais
    4. **Chamado (retorno):** põe o valor de retorno no lugar combinado (`$v0`), restaura registradores e `$sp`, desvia para o endereço de retorno (`jr $ra`)
    5. **Chamador:** recupera o valor devolvido e continua
TEXTO: **Árvore de ativação:** cada nó é uma ativação; os filhos de um nó são as ativações que ele chamou, da esquerda para a direita, na ordem das chamadas. **Propriedade:** a pilha de controle, num dado instante, contém exatamente o caminho da raiz até o nó em execução.
PASSOS Três estratégias de alocação:
    1. **Estática:** endereço fixo em tempo de compilação; não permite recursão nem tamanho dinâmico (globais; FORTRAN 77)
    2. **Em pilha:** um quadro por ativação, LIFO; permite recursão; o quadro morre no retorno (locais em C e Java)
    3. **Em heap:** blocos com tempo de vida arbitrário; liberação manual (`free`) ou por coleta de lixo
CODIGO (Convenção de chamada do MIPS):
    $a0–$a3   argumentos           $v0–$v1  valores de retorno
    $ra       endereço de retorno  $sp      topo da pilha
    $fp       base do quadro atual (opcional)
    $t0–$t9   temporários: o CHAMADOR salva se precisar deles depois
    $s0–$s7   salvos: o CHAMADO salva antes de usar
    
    jal f     # $ra := PC + 4;  PC := f
    jr  $ra   # PC := $ra
PREVEJA: Qual vínculo aponta para o quadro de QUEM CHAMOU a função?
    (     ) Vínculo de acesso (estático)
    (certa) Vínculo de controle (dinâmico)
    (     ) Endereço de retorno
    EXPLICACAO: Controle/dinâmico = cadeia de CHAMADAS. Acesso/estático = cadeia de ANINHAMENTO no texto (útil em linguagens com funções aninhadas, como Pascal). O endereço de retorno aponta para uma INSTRUÇÃO, não para um quadro.

DESTAQUE EXAM_TIP: Questão clássica: 'desenhe o registro de ativação e diga quem preenche cada campo'. Parâmetros, valor de retorno (espaço) e endereço de retorno: o chamador. Locais, temporários e registradores salvos: o chamado. Liste de cima para baixo nessa ordem.
DESTAQUE WATCH_OUT: Endereço de retorno ≠ vínculo de controle. O primeiro diz para qual INSTRUÇÃO voltar; o segundo, qual QUADRO volta a ser o atual.

     palco: MIPS | total | $t0
2. [BYTE] Contas só acontecem entre registradores, dentro do processador.

=== AULA DE LEITURA [STORY] A bancada pequena e a despensa enorme
[NARRADOR] Última estação da Forja do Código. O TAC chega em fichinhas; do outro lado da esteira sai um arquivo .asm que o MARS vai rodar.
[BYTE] MIPS... Eu fico com medo só de ver tanto cifrão.
[PROF] Fica tranquilo: é uma cozinha. O processador é um cozinheiro com uma **bancada pequenininha** e uma **despensa enorme** no fim do corredor.
TEXTO: Na bancada cabem só 32 potinhos com etiqueta (`$t0`, `$t1`, ...). Ele **só cozinha o que está na bancada**: para usar a farinha, vai à despensa buscar (**lw**) e, quando termina, leva o resultado de volta (**sw**).
PASSOS O mapa da analogia:
    1. Potinhos da bancada → **registradores** (`$t0`–`$t9`, `$s0`–`$s7`, ...): rápidos e poucos
    2. Prateleiras da despensa → **memória**, declarada na seção **.data** (`x: .word 0`)
    3. Buscar na despensa → **lw** (*load word*); guardar de volta → **sw** (*store word*)
    4. 'Use 2 ovos' (não precisa buscar nada) → **li** (*load immediate*: uma constante)
    5. Misturar dois potinhos num terceiro → **add / sub / mul / div**
    6. O caderno de passos → seção **.text**, começando no rótulo **main:**
    7. Post-it 'se faltou ovo, pule para L0' → **desvios** (beq, bne, j) e **rótulos**
CODIGO (A receita traduzida, uma ficha TAC por bloco):
    # x = a + b * 2     (TAC: t1 = b * 2 ; t2 = a + t1 ; x = t2)
    lw   $t1, b         # busca b na despensa
    li   $t2, 2         # pega a constante 2
    mul  $t3, $t1, $t2  # mistura
    sw   $t3, t1        # guarda na prateleira t1
    lw   $t1, a
    lw   $t2, t1
    add  $t3, $t1, $t2
    sw   $t3, t2
    lw   $t0, t2
    sw   $t0, x

    (certa) 4
    (     ) 10

DESTAQUE WATCH_OUT: `t1` (sem cifrão) é uma **prateleira** da despensa: uma variável na .data que o gerador criou para o temporário. `$t1` (com cifrão) é um **potinho** da bancada. Nomes parecidos, lugares diferentes! No seu trabalho, chamar os temporários de `_t1` evita confusão.

=== AULA DE LEITURA [SOCRATIC] Por que tanto lw e sw?
[PROF] Vou só fazer perguntas. Você vai descobrir sozinho como se gera código MIPS.
REVELAR: No MIPS, `add` só aceita registradores. Então como somar duas variáveis que estão na memória?
    RESPOSTA: Primeiro trazê-las para registradores (lw), somar, e devolver o resultado à memória (sw). O MIPS é uma arquitetura **load/store**: só lw/sw tocam a memória; todo o resto trabalha em registradores.
REVELAR: E se um operando é uma constante, como em b * 2?
    RESPOSTA: Não há o que buscar na memória: usa-se `li $t2, 2` (carrega imediato). Para somar uma constante existe até atalho: `addi $t3, $t1, 2`.
REVELAR: Onde as variáveis e os temporários 'moram' no estilo do trabalho prático?
    RESPOSTA: Na seção .data, uma `.word` para cada um: `x: .word 0`. É simples e sempre funciona, o preço é acessar a memória o tempo todo.
[BYTE] Mas e o if? MIPS não tem chaves...
REVELAR: Como fazer 'se a > b, faça X; senão, faça Y' tendo só 'pule para tal linha'?
    RESPOSTA: Calcule a condição num registrador (sgt/slt deixam 1 ou 0). Se ela for 0, pule para o rótulo do else (`beq $t3, $zero, L0`). No fim do then, um `j L1` pula o else.
REVELAR: E o while? Que desvio faz ele repetir?
    RESPOSTA: Um `j` para TRÁS, de volta ao rótulo do teste. O teste fica no começo: se falhar, um desvio para FRENTE sai do laço.
PREVEJA: Para que serve o registrador `$zero`?
    (     ) Guarda o último resultado que deu zero
    (certa) Vale sempre 0 — ótimo para comparar com 'falso' (beq $t3, $zero, L0) e para copiar
    (     ) Conta quantas instruções já rodaram
    EXPLICACAO: Escrever nele não adianta: ele é fixo em 0. `beq $t3, $zero, L0` se lê 'se $t3 é falso, pule'. E `move $t0, $t1` é, por baixo, uma soma com `$zero`.
REVELAR: Como o programa imprime algo, se o processador nem sabe o que é tela?
    RESPOSTA: Pede ao sistema: põe o código do serviço em `$v0` (1 = inteiro, 4 = string, 10 = sair), o argumento em `$a0` (o número, ou o endereço da string, obtido com `la`) e executa `syscall`.
[BYTE] E dá pra gastar menos lw e sw?
REVELAR: Em x = a + b * 2, o gerador ingênuo faz 7 acessos à memória. Quantos são realmente necessários?
    RESPOSTA: Três: buscar a, buscar b e guardar x. Os temporários podem viver em registradores: `lw $t0, a / lw $t1, b / li $t2, 2 / mul $t1, $t1, $t2 / add $t0, $t0, $t1 / sw $t0, x`. Decidir quem fica em qual registrador é a **alocação de registradores**.
WIDGET MIPS gramatica= entrada=a + b * 2 legenda=Conte os lw e sw do gerador ingênuo e compare com a versão de 3 acessos.
DESTAQUE BRAIN_POWER: Por que não pôr TUDO em registradores? Porque são só 32 (e vários reservados). Quando faltam, alguém volta para a memória, o famoso **spill**. Escolher bem quem fica é um problema difícil (vira coloração de grafos!).

=== AULA DE LEITURA [FORMAL] Esquemas de tradução TAC → MIPS
TEXTO: **Gerador de código:** fase final, que mapeia a representação intermediária (TAC) em instruções da máquina-alvo. Problemas centrais: **seleção de instruções**, **alocação de registradores** e **ordem de avaliação** (Livro do Dragão, cap. 8).
CODIGO (Registradores MIPS (32 bits) usados no trabalho):
    $zero         constante 0
    $v0–$v1       valores de retorno / código da syscall
    $a0–$a3       argumentos
    $t0–$t9       temporários (não preservados na chamada)
    $s0–$s7       salvos (preservados na chamada)
    $sp $fp $ra   topo da pilha, base do quadro, endereço de retorno
CODIGO (O subconjunto do MIPS que um gerador simples precisa):
    lw   rd, rot       rd := Mem[rot]
    sw   rs, rot       Mem[rot] := rs
    li   rd, k         rd := k                    (pseudo)
    la   rd, rot       rd := endereço de rot      (pseudo)
    add  rd, rs, rt    rd := rs + rt     (sub, mul, div análogos)
    addi rd, rs, k     rd := rs + k
    slt  rd, rs, rt    rd := (rs < rt) ? 1 : 0    (sgt, seq: pseudo)
    beq  rs, rt, L     se rs = rt, desvia para L  (bne: se ≠)
    j    L             desvia para L
    syscall            serviço em $v0: 1 int, 4 string, 10 sair
CODIGO (Esquema TAC → MIPS no estilo 'tudo na memória' (o do jogo e do trabalho)):
    gera(x = y op z):
        carrega("$t1", y);  carrega("$t2", z)
        emite(opMips(op) + " $t3, $t1, $t2")
        emite("sw $t3, " + x)
    
    gera(x = y):
        carrega("$t0", y);  emite("sw $t0, " + x)
    
    carrega(r, v):
        se v é constante: emite("li " + r + ", " + v)
        senão:            emite("lw " + r + ", " + v)
CODIGO (Esquemas para comandos (rótulos novos a cada uso)):
    if (E) S1 else S2              while (E) S
        <E em $t3>                 Linicio:
        beq $t3, $zero, Lelse          <E em $t3>
        <código de S1>                 beq $t3, $zero, Lfim
        j Lfim                         <código de S>
    Lelse:                             j Linicio
        <código de S2>             Lfim:
    Lfim:
PREVEJA: Pelo esquema 'tudo na memória', quantas instruções MIPS gera x = a + b * c?
    (     ) 6
    (     ) 8
    (certa) 10
    EXPLICACAO: Dois operadores × 4 instruções (lw, lw, op, sw) = 8, mais 2 da cópia x = t2 (lw, sw) = 10.
WIDGET MIPS gramatica= entrada=a + b * c legenda=Conte as instruções: 10.
TEXTO: **Custo:** num processador real, acessar a memória é bem mais caro que usar um registrador. O critério clássico de qualidade é **minimizar lw/sw**: manter valores vivos em registradores, reaproveitar resultados e eliminar pares `sw t1` / `lw t1` consecutivos.
DESTAQUE EXAM_TIP: Em 'gere o código MIPS', escreva SEMPRE as duas seções (.data com variáveis e temporários; .text começando em main:), comente cada bloco com a instrução TAC correspondente e termine com `li $v0, 10` + `syscall`. Sem isso o MARS até para ('dropped off bottom'), mas o professor desconta.
DESTAQUE WATCH_OUT: Em `lw` e `sw` o REGISTRADOR vem primeiro nos dois, mas a direção muda: `lw $t1, a` leva a → $t1; `sw $t1, a` leva $t1 → a. E o `div` de três operandos é pseudo: o real é `div $t1, $t2` seguido de `mflo $t3` (quociente; o resto fica em hi, lido com `mfhi`).

DESTAQUE MNEMONIC: **'Busca, busca, mistura, guarda.'** Toda instrução TAC x = y op z vira: lw (busca y), lw (busca z), op (mistura), sw (guarda em x). Ritmo de samba: 1, 2, 3, 4.
DESTAQUE MNEMONIC: **Load = Leva para a bancada; Store = Salva na despensa.** Nos dois, o registrador vem PRIMEIRO: `lw $t1, a` e `sw $t1, a` — só muda a direção da seta.
DESTAQUE MNEMONIC: **Família de registradores pela inicial:** `$t` = **t**emporário (pode sujar), `$s` = **s**alvo (guarde antes de usar), `$a` = **a**rgumento, `$v` = **v**alor de retorno, `$ra` = **r**eturn **a**ddress, `$sp` = **s**tack **p**ointer.
DESTAQUE MNEMONIC: **beq = Branch if EQual (pula se igual); bne = Branch if Not Equal.** O if testa AO CONTRÁRIO: 'se a condição é falsa (igual a $zero), pula o then'.
DESTAQUE MNEMONIC: **syscall 1, 4, 10: 'um número, uma fila de letras e dez-liga'.** 1 imprime inteiro; 4 imprime string ('fila' tem 4 letras; use `la $a0, msg`); 10 encerra (dez... desliga!).

    (     ) Para main

################ ASSUNTO REG_ALLOC: Alocação de registradores  prereqs=[CODEGEN_MIPS]
FICHA: Alocar registradores é manter os temporários em registradores em vez da memória: calcula-se a vivacidade de trás para frente (in = use ∪ (out − def)), liga-se no grafo de interferência quem está vivo ao mesmo tempo e colore-se o grafo com k cores (k registradores); se não der, algum temporário é derramado (spill) para a memória.

=== AULA DE LEITURA [STORY] Poucas bancadas na cozinha
[NARRADOR] Cozinha de restaurante em dia de casamento. A despensa no subsolo guarda tudo, mas cada viagem de escada leva uma eternidade. Lá em cima há só três bancadas.
[BYTE] É a cozinha da aula de MIPS! Bancada é registrador, despensa é memória.
[PROF] Isso. E o chef novo faz uma burrice: termina o molho, LEVA para a despensa, e cinco minutos depois desce de novo para BUSCAR o mesmo molho. É o código ingênuo: `sw` seguido de `lw` do mesmo temporário.
[PROF] O chef experiente pensa diferente: 'O molho vai ser usado logo, fica numa bancada. Quando o molho for usado pela última vez, a bancada fica LIVRE para outra preparação.'
PASSOS Cozinha → alocação de registradores:
    1. Cada preparação intermediária (molho, massa) é um **temporário** (t1, t2, ...).
    2. Cada bancada é um **registrador**. Só há k bancadas.
    3. Do momento em que a preparação fica pronta até seu ÚLTIMO uso, ela está **viva** e ocupa uma bancada: esse é o seu **intervalo de vida**.
    4. Duas preparações vivas AO MESMO TEMPO não podem dividir bancada: elas **interferem**.
    5. Dar uma bancada a cada preparação, sem que vizinhas briguem, é **colorir um grafo**: cada cor é um registrador.
    6. Se não houver bancadas suficientes, alguma preparação desce para a despensa e é buscada de novo quando precisar: é o **spill** (derramamento).
DESTAQUE REAL_WORLD: É o mesmo problema de pintar o mapa do Brasil: estados que fazem fronteira não podem ter a mesma cor. Na alocação, a 'fronteira' é estar vivo ao mesmo tempo. Quatro cores bastam para qualquer mapa plano, mas o grafo de um programa não é um mapa: às vezes precisa de mais.
PREVEJA: Em r = a * b + c * d: t1 = a * b fica pronto; depois t2 = c * d; depois t3 = t1 + t2. Quais temporários precisam de bancadas diferentes?
    (certa) t1 e t2
    (     ) t1 e t3
    (     ) t2 e t3
    (     ) Todos os três
    EXPLICACAO: Quando t2 fica pronto, t1 ainda espera para ser usado: os dois estão vivos juntos. Já t3 nasce exatamente quando t1 e t2 morrem (são usados pela última vez), então t3 pode reaproveitar a bancada de qualquer um deles.
WIDGET REGALLOC gramatica= entrada=a * b + c * d legenda=Veja os vivos, o grafo (só uma aresta: t1—t2) e a coloração com 2 registradores.
REVELAR: Quantas viagens à despensa (lw + sw) o código ingênuo faz nesse cálculo, e quantas depois da alocação?
    RESPOSTA: Ingênuo: 11 (7 lw + 4 sw). Com 2 registradores: 5 (4 lw das variáveis a, b, c, d + 1 sw do resultado r). Menos da metade!
DESTAQUE NO_DUMB_QUESTIONS: P: Por que não usar logo um registrador diferente para cada temporário? R: Porque um programa de verdade tem milhares de temporários e o MIPS tem 32 registradores (e vários reservados). Reaproveitar bancadas é obrigatório.

=== AULA DE LEITURA [FORMAL] Alocação por coloração: definição de prova
TEXTO: Para cada instrução i: **use[i]** = variáveis lidas por i; **def[i]** = variáveis escritas por i. Uma variável x está **viva** num ponto P se existe um caminho de P até um uso de x que não passa por definição de x.
CODIGO (Equações de vivacidade):
    Vivacidade (análise de fluxo de dados PARA TRÁS):
        out[i] = ∪ in[s]   para cada sucessor s de i     (no fim: out = ∅)
        in[i]  = use[i] ∪ (out[i] − def[i])
    Num bloco básico (sem desvios), o único sucessor de i é i + 1:
        percorra de i = n−1 até 0, com out[n−1] = ∅.
    Com laços: repita até nenhum in/out mudar (ponto fixo).
TEXTO: **Intervalo de vida** de x: os pontos do programa em que x está viva. **Grafo de interferência** G = (V, E): V = temporários; {x, y} ∈ E se x é definido numa instrução em que y ∈ out (y ≠ x). (Refinamento clássico: numa cópia x = y, não se liga x a y, para permitir que dividam o registrador.)
TEXTO: **Alocação com k registradores** = **k-coloração** de G. Decidir se G é k-colorível é NP-completo para k ≥ 3, por isso usamos heurísticas.
CODIGO (Simplificar, empilhar, colorir):
    Chaitin(G, k):
        pilha ← vazia
        enquanto G não vazio:
            se existe n com grau(n) < k:          // SIMPLIFICAR
                remova n de G; empilhe n
            senão:                                // candidato a SPILL
                escolha n (ex.: maior grau, menor custo); remova; empilhe
        enquanto pilha não vazia:                 // SELECIONAR
            n ← desempilha
            se sobra cor não usada pelos vizinhos já coloridos: dê a menor
            senão: n é DERRAMADO (sw após def, lw antes de cada uso)
TEXTO: **Por que funciona**: se grau(n) < k, então, por pior que seja a coloração dos vizinhos, sobra uma cor para n. Remover n não atrapalha; colorimos na volta. Spill só acontece quando todo nó restante tem grau ≥ k.
PREVEJA: Um grafo tem um nó n de grau 5 e k = 4. O que é VERDADE?
    (     ) n certamente será derramado
    (certa) n não pode ser simplificado agora, mas pode acabar colorido se dois vizinhos receberem a mesma cor
    (     ) O grafo não é 4-colorível
    EXPLICACAO: Grau ≥ k só torna n um CANDIDATO. Na seleção, se os vizinhos repetirem cores, sobra cor para n. Por isso o spill de Chaitin é 'otimista' na versão de Briggs.
WIDGET MIPS_RUN gramatica=# Convenção: $s0..$s7 são SALVOS PELO CHAMADO; $t0..$t9 não (o chamador que se cuide) ;         .data ; x:      .word 0 ;         .text ; main: ;         li   $s0, 7           # main guarda um valor importante em $s0 ;         li   $a0, 5 ;         jal  dobro            # chama dobro(5) ;         add  $s0, $s0, $v0    # 7 + 10: $s0 ainda vale 7! ;         sw   $s0, x ;         li   $v0, 1 ;         move $a0, $s0         # imprime 17 ;         syscall ;         li   $v0, 10 ;         syscall ; dobro: ;         addi $sp, $sp, -4 ;         sw   $s0, 0($sp)      # vai usar $s0? então SALVA antes... ;         add  $s0, $a0, $a0 ;         move $v0, $s0 ;         lw   $s0, 0($sp)      # ... e RESTAURA antes de voltar ;         addi $sp, $sp, 4 ;         jr   $ra entrada= legenda=Convenção do MIPS: $s0 é salvo pelo CHAMADO. dobro usa $s0, mas salva e restaura; main encontra o 7 intacto e imprime 17.
TEXTO: **Convenção MIPS**: $t0–$t9 são **salvos pelo chamador** (caller-saved): uma função pode sobrescrevê-los à vontade. $s0–$s7 são **salvos pelo chamado** (callee-saved): quem os usa salva na pilha e restaura antes do `jr $ra`. Regra prática: valor que atravessa uma chamada → $s; valor de vida curta → $t.
DESTAQUE EXAM_TIP: Roteiro de prova: (1) TAC; (2) tabela use/def/out/in DE BAIXO PARA CIMA; (3) arestas: def × out; (4) Chaitin com a pilha escrita; (5) mapa temporário → registrador; (6) se pedir, o MIPS e a contagem de lw/sw antes × depois.
REVELAR: Escreva a equação de vivacidade e a regra de interferência.
    RESPOSTA: in[i] = use[i] ∪ (out[i] − def[i]); out[i] = ∪ in dos sucessores. x e y interferem se x é definido numa instrução em que y está vivo na saída (y ∈ out[i]).

=== AULA DE LEITURA [MNEMONIC] Pinte o mapa da cozinha
DESTAQUE MNEMONIC: **VIGOR**: **VI**vacidade → **G**rafo → c**O**lorir → **R**egistradores. (E se faltar cor? Spill: 'derrama no chão'.)
TEXTO: **Palácio da memória**: na Forja do Código, ao lado da Montadora MIPS, fica o **Ateliê de Coloração** . Na parede, um mapa com bolinhas (os temporários). O pintor tem só k latas de tinta (registradores). Bolinhas ligadas por fio não podem ter a mesma cor. A que sobrar sem tinta vai para o porão (a memória).
DESTAQUE MNEMONIC: **Vivacidade se faz como desfazer a mala: de trás para frente.** O último item que entrou é o primeiro que sai. Comece no fim do código com out = { }.
DESTAQUE MNEMONIC: **in = use ∪ (out − def)** se lê: 'está vivo antes quem eu USO agora, mais quem estava vivo depois e eu NÃO matei'. Def mata, use ressuscita.
DESTAQUE MNEMONIC: **Interferência = 'nasceu enquanto o outro estava vivo'.** Quem é definido ganha aresta com todo mundo do out daquela instrução.
